# Start small

Use [the workspace reader](examples/start-here/extension.ts) first. defineExtension emits the existing package contracts; useApiRead binds reads to the view's scope, visibility and cancellation. Write a separate Node server.ts only when providing a server API. Set serverEntry in the definition; build supplies an empty tools array when omitted.

The source and tests are included. Follow the named type/function first; read host internals only for an operation the public API cannot provide. defineExtension covers ordinary surfaces, API providers and declared assets; the CLI packs asset files and generates their integrity hashes, so byteLength/sha256 are never author inputs.

A requirement selects an API/version; a named plugin dependency also declares the APIs used from it. Shared providers are explicitly selected in Settings. Installation grants and the authenticated session both constrain access. Discovery describes actual availability; a plausible API name or built-in panel does not prove an API exists. Missing/incompatible dependencies and revoked access must stay visibly unavailable.

useApiRead is for declared read methods. Use [bindApi/bindStreamApi](src/capabilities.ts) for writes or streams, pass cancellation, and handle their actual contract. Do not retry writes on a different provider. Registration, a view or a read subscription never supplies write authority.

Run build/check on the real output, then verify the installed feature. receipt.json identifies checked bytes; it explicitly does not claim installation or behavior. The packer resolves modules against the package's realpath'd directory, so a dependency reached through a store link, a workspace symlink, or a real install bundles as the same module and its transitive dependencies resolve beside its real target. Generated module labels — banner comments, wrapper keys, glob names, JSX debug fileName — are rewritten to a canonical `node_modules/<name>/…` form taken from the dependency's own package.json, so emitted bytes are identical across the build's working directory, checkout depth, and those link layouts. The limits are deliberate: distinct modules that would claim one canonical name keep their emitted labels rather than merge, and a dependency with neither a package name nor a node_modules path (a bare `file:` link) keeps its location-dependent spelling. User-authored strings and templates are never rewritten — the rewriter only touches positions esbuild itself generates (prologue helpers, module wrappers under their own banner comments, the jsx-dev-runtime's own metadata objects), so data that merely looks like a path, or user code that names a helper like `__esm` or exports a `jsxDEV` member, survives verbatim. One boundary is worth stating: code that exactly reproduces the bundler's emitted shape — a top-level `var require_*`/`init_*` bound to the bundler's own helper, or a hand-authored `jsxDEV` call into the real `react/jsx-dev-runtime` — meaning the file that specifier resolves to from your package, or the host React namespace — is indistinguishable from generated output and is treated as generated. A file that merely shares the runtime's path shape inside an unrelated package is not the runtime and is left alone. Keep a small feature assertion alongside your source. Platform maintainers own the shared lifecycle/dependency regression suite; authors should not recreate it.

Ordinary React imports and a component library work in authored sources. The CLI binds React and JSX imports to the host runtime; React DOM imports require a separate host contract and are currently rejected.
