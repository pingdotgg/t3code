# Host integration reference

For plugin authors, start with [the tested source example](examples/start-here/extension.ts). This reference is for implementing a T3 host.

## View contract

A surface declares title, supported placements/clients, scope, required service capabilities and restoration version. Its `createView(session)` returns a renderer and optional idempotent cleanup. `validateRestore` accepts `null` for fresh resources and validates its saved JSON. The host allocates viewer IDs; two viewers may reference one domain resource. The renderer type is chosen by the client, independently of the JSON protocol.

The host supplies immutable-by-copy context with environment/project/thread/resource and optional workspace revision. `session.invoke(capability,input)` pins that context, checks declared capability and host authorization on every call, bounds input/output, and passes cancellation to the domain adapter. It never accepts a plugin-selected target context. The host adapter still must validate authenticated ownership and resource relationships. Do not expose credentials, arbitrary RPC dispatch, database handles, filesystem traversal, PTY termination, or orchestration control through a generic service. Custom host integrations may register narrow services in their own namespace. Installable authors must use actually available public catalogue APIs and declared dependencies; a plausible service name is not an implemented adapter.

`session.publish(sequence,state)` replaces the latest JSON presentation. Sequence numbers are strictly increasing within one generation; duplicate/old/hidden/disposed publications return false. Notifications coalesce within a microtask, storing one current snapshot rather than an event queue. The default budget is 64 KiB per JSON value, nesting depth 32, 64 open viewers, eight pending service calls per viewer and a ten-second deadline. Each adapter must bound its own upstream stream; the host does not make synchronous trusted code preemptible. `session.save(state)` validates bounded restoration data. State getters return copies; modifying them cannot change host state.

`hide` preserves the controller, renderer and session, aborts activity calls and rejects new calls/publications. `session.visible` and `onVisibility` let terminal/media renderers stop expensive presentation work; visibility hooks must suspend owned streams. `show` resumes the same instance. The lifetime `signal` remains live while hidden. `close`, disable, context replacement and shutdown abort lifetime and activity, call all `onDispose` cleanups, and dispose the renderer controller once. Closing one viewer never calls domain terminate. `move` changes placement without recreating a view.

`updateContext` creates a new generation and clears presentation before the new factory runs. Old service responses and publications cannot appear in the new context, including a workspace revision change. A different resource resets restoration data to `null`. An adapter must honor cancellation for actual backend work; cancellation does not undo a completed external effect. Register cleanup immediately through `onDispose`, including before asynchronous activation. Late factory completion after cancellation is disposed. Service exceptions reject only that call; factory/visibility/render exceptions mark only that view failed. Promise rejection in plugin-owned callbacks remains the plugin's responsibility.

The shell persists `host.records()` in its existing layout store and restores each `ViewRecord`. Unknown, disabled, missing-capability, unsupported-client, invalid-state and incompatible-state contributions retain their record and readable fallback. Restore never creates a resource in the host itself; extension factories must observe existing resources when `session.restoring` is true. Enable does not automatically reopen hidden or failed views: explicitly `show` or restore after grants/reconnection are known.

## React shell integration

Import `ExtensionSurface`, `SurfaceRenderer`, and `SurfaceRendererProps` from `@t3tools/extension-sdk/react`. Create one `createExtensionHost<SurfaceRenderer>` for the client scope. A trusted contribution returns a React component receiving `{snapshot}`. Mount `<ExtensionSurface host={host} viewId={id} className="your-layout" style={{ height: "100%", minHeight: 0 }} />` inside the existing tab/dock shell. The optional `className` and `style` belong to the host layout and apply to the outer wrapper in ready, hidden and fallback states. Give full-height terminal/browser descendants a definite wrapper height through these props. Hidden views force inline `display: none` over the supplied style while retaining their subtree; showing restores the supplied display style. The adapter subscribes to that viewer, reports render exceptions through `host.fail`, resets its boundary on generation change, and preserves the renderer subtree behind a hidden wrapper on hide/show. Keep the adapter mounted while hidden if retaining local React state matters. A custom `fallback(snapshot)` may render retry/close controls; default fallback is text in a status element.

The right-panel store remains the layout/focus owner. Use its existing user-action revision guard before calling `open` from delayed proactive work. Route sidebar, menu, palette and keybinding entries through the same host command at integration; do not let asynchronous data completion choose active tabs. The SDK deliberately does not create a competing layout or focus manager. A surface that captures terminal input declares `claimsTerminalFocus` on its descriptor; the host then tags the surface frame `data-terminal-owner="extension"`, so the capture-phase dispatcher leaves focused-terminal commands (split, splitVertical, new, close) and already-consumed keys to that surface's own keymap rather than acting on a native terminal. A claiming surface must implement those bindings itself — the host leaves the event untouched. The drawer toggle (`terminal.toggle`) stays host-owned: focused in a claiming surface in the extension dock it hides that dock, as it hides the native drawer from inside it; anywhere else it drives the native drawer. Store the generic contribution `surfaceId` and resource record, then resolve registered metadata/renderer instead of adding six kind cases. Files and Diff can retain their existing engines; Terminal and Browser keep shared domain sessions; Version Control retains repository/review write authorization; Agents remains presentation-only. Host service adapters and their import boundaries must be reviewed in the migration lanes.

## Coverage and limits

Focused tests cover public lifecycle, hidden identity, independent viewers, scope/revision races, timeouts, late factory completion, capability revocation, invalid payloads, bounded updates, failures and 100 lifecycle cycles. They are contract tests, not UI parity or performance measurements. React Native needs a native renderer and bridge; Electron, authenticated local/remote/relay/tunnel domain services, all providers, V2 adapters, compositor performance and accessibility journeys require separate integration verification. The SDK package does not itself serve endpoints. The application environment runtime supplies authenticated installation and API transports; domain support must still be discovered and verified. Broader orchestration operations, structured attachments, asynchronous context resolution and untrusted isolation remain later phases.

For a shell exit transition, `retainHiddenPresentation` keeps a hidden view painted until the shell removes it. Activity remains hidden/cancelled and the wrapper is inert and aria-hidden. The default still applies display:none. The shell must end the transition and conceal/unmount the view; this option does not resume extension work.

## Composer context and read-only message cards

An extension may register optional `composerContexts` and `messageDecorations` descriptor/implementation arrays alongside its surfaces. Both use namespaced IDs and explicit clients. `@t3tools/extension-sdk/context` exports the portable types and text helpers. See [the issue-context fixture](examples/issue-context/issue-context.mjs), which uses only public SDK imports and clearly labels its static data.

The web composer lists registered context contributions under Add context. Its synchronous `select(ViewContext)` returns a title, plain text and optional HTTP(S) source URL. The host stamps contribution/package identity, capture time and originating resource scope. The complete captured snapshot is inserted as readable prompt text; a removable preview and core inline editor chip are derived from it. Core history formatting shows title/source/content without transport metadata, while copy/export retain the original source. Existing draft persistence, stash, prompt recall and failed-send recovery own that string. Unregistering the extension does not delete its captured text. Add the context again to capture a new revision; there is no automatic refresh.

Each selection allows 8 KiB of UTF-8 text, at most eight snapshots and 32 KiB of serialized context per prompt. Text containing the composer's reserved object-replacement character is rejected. The current prompt string freezes at the existing send boundary before asynchronous uploads, and the existing server command admits that exact submitted text. This is a snapshot captured on selection, not a live server read at admission. No new attachment kind or wire field is introduced. Provider input validation still applies.

A message decorator receives one copied immutable message with environment/thread/message identity and returns a bounded plain card or null. The web host invokes it only for a visible user-message row. It retains the original message text alongside the card, contains thrown errors, and stops rendering the card after unregister. Decorations cannot edit messages or submit turns. The first version supports synchronous pure projection, not asynchronous fetching or arbitrary custom renderers. Plain fallback remains usable without a renderer; native clients have no contribution UI in this implementation.

## Trusted environment packages

The public @t3tools/extension-sdk/environment export describes t3-extension.json format-1 and format-2 packages. Format 2 adds dependencies, provides and requires plus typed API calls; see the authoring guide. The compatible format-1 shape contains the existing manifest, optional relative bundled client/server ESM entries, and a bounded read-only tool catalog. At least one entry is required; client contributions need a client entry and tools need a server entry. Installation grants are separate host policy. validateEnvironmentPackage checks portable descriptor shape; the runtime must compile tool input schemas with strict draft7 Ajv and reject external references.

The server entry defaults to a ServerExtension object whose tool IDs match the descriptor. Each handler receives a ToolSession with verified context, cancellation signal and named host-capability invocation. validateServerExtension checks that executable catalog. The client entry defaults to a synchronous ClientFactory; use its injected React and asynchronous invokeApi/discoverApis bindings (or invokeTool for existing tools) to return an existing Extension<SurfaceRenderer>. Do not import or bundle another React runtime.

The public @t3tools/extension-sdk/workspace export defines WORKSPACE_READ_TEXT, WorkspaceReadTextInput, WorkspaceReadTextResult and their validators. Input is one forward-slash relative path; output is complete bounded JSON with text, source byte length and truthful truncation. Canonical filesystem containment, live environment/project resolution and authorization remain host duties.

The [installable workspace reader](examples/installable-workspace-reader/README.md) supplies self-contained client/server entries with an actual host-backed read tool and explicit captured text. These package contracts do not themselves install code, expose an RPC endpoint or deliver tools to providers. A host implementing those boundaries must retain its own activation, grant, timeout and process-lifetime policies. Trusted packages are not sandboxed.

Format-4 packages can carry bounded, immutable WASM/font/binary assets. Use the
[installed asset example](examples/installable-package-assets/README.md) and
[asset authoring contract](AUTHORING.md#declared-renderer-assets-format-4).
Availability requires an environment and client that both support format 4;
this does not establish native panel or mobile parity.

The public capabilities export also provides defineStreamApi, bindStreamApi and
TypedApiStreamFrame for typed, cancellable API streams. The
[independent live terminal output example](examples/installable-terminal-live-output/client.mjs)
owns its client and namespaced forwarding API. It is a read-only diagnostic
consumer, not a replacement for the interactive Terminal panel.
