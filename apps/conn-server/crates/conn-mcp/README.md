# conn-mcp

`/mcp` for the Conn Server: the T3 tool server that agents inside a thread, and outside callers
such as Orbit's Swamp, call over MCP. The T3 server (`apps/server/src/mcp/McpHttpServer.ts`) is
the reference; this crate is our own implementation on the `Engine` trait.

| Path                              | Holds                                                             |
| --------------------------------- | ----------------------------------------------------------------- |
| `src/transport.rs`                | Streamable HTTP, JSON-RPC, MCP sessions                           |
| `src/credentials.rs`              | Agent tokens per provider session                                 |
| `src/catalog.rs`, `catalog.jsonl` | The T3 tool definitions we serve, generated; argument checks      |
| `src/null-arguments.txt`          | Arguments whose schema takes `null`, generated by `gen-tools.mjs` |
| `src/running-task-next.txt`       | The `next` text of a running task, generated by `gen-tools.mjs`   |
| `src/tools/`                      | The handlers: threads, tasks, projects and environment            |
| `src/view.rs`                     | Engine rows shaped as the tool results                            |
| `tools.implemented`               | The tools we serve, one per line                                  |
| `tools/gen-tools.mjs`             | Writes `catalog.jsonl` from `apps/server`; `--check` finds drift  |
| `tools/parity.mjs`                | Same calls on the T3 server and the Conn Server; compares results |
| `src/outside-hidden.txt`          | Tools that act as the calling thread, hidden from outside clients |
| `src/subagent-hidden.txt`         | Tools hidden from delegated children (the PR watch tools)         |
| `fixtures/ts-tools-list.json`     | A live T3 server's `tools/list` (42 tools, outside caller)        |
| `fixtures/t3-tool-names.txt`      | Every tool `apps/server` registers, generated by `gen-tools.mjs`  |

The route is `crates/conn-server/src/routes/mcp.rs`; `serve.rs` builds the service.

## Transport

Measured on a live T3 server at the pinned commit (`tools/mcp-client.mjs` drives both servers).

- One endpoint, `POST /mcp`, protocol **2025-06-18**. Any `initialize` version gets 2025-06-18,
  as the T3 server answers. The T3 server also serves sessionless 2026-07-28; no T3 caller uses it.
- **Sessions:** `initialize` returns `Mcp-Session-Id`. Every later request names it: missing →
  400 with JSON-RPC `-32600` (`MCP-Session-Id header is required…`), unknown → 404, `DELETE` → 204. Ours are bound to the credential that opened them, capped at 256, idle after 24 h.
- Replies use JSON and a `mcp-protocol-version` header. A successful `tool_search` with
  matches sends SSE: `notifications/tools/list_changed` before the result. Notifications get
  202. `GET` is 405 (`allow: POST, DELETE`).
- Checks in the T3 order: auth 401, an `Origin` header 403, a content type other than JSON 415,
  an `Accept` without both `application/json` and `text/event-stream` 406, a bad body `-32700`,
  a JSON-RPC batch 400, an unknown `mcp-protocol-version` 400 (`-32022`).
- Methods: `initialize`, `ping`, `tools/list`, `tools/call`, `logging/setLevel`; others `-32601`.
  `tools/list` is not paged. A deferred client lists four direct tools plus its search results.
- `tools/call`: success is `{content: [text JSON], structuredContent, isError: false}`; a tool
  failure is `{content: [text OrchestratorMcpFailure JSON], isError: true}`; an unknown tool,
  an undeclared argument, a missing key, or a wrong type is JSON-RPC `-32602`
  (`Invalid parameters for tool 'X': Unknown argument "y". Accepted arguments: …`). `null` for an
  optional argument counts as omitted, unless its schema takes `null` (`src/null-arguments.txt`,
  such as `t3_queue`'s `beforeRunId`). Type, length, range and literal failures use Effect's
  words: `Expected string` (`| null` for an optional field), `Expected a value with a length of
  at most 4000`, `Expected a value between 1 and 100`, `Expected an integer`, `Expected "a" |
  "b"`; parity checks each against the T3 server. String lengths count UTF-16 units.
  `environmentId` other than this environment's is
  `capability_denied`, as the T3 server answers with linked environments off.

## Auth

| Caller            | How it authenticates                                                                             | Scope                                                            |
| ----------------- | ------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------- |
| Agent in a thread | `Authorization: Bearer <token>` from `McpService::issue_thread_credential`                       | Acts as its thread: default target, modes capped at the thread's |
| Outside client    | An environment bearer session (paired device, `t3 auth session issue`) with `orchestration:read` | `orchestration:operate`: any runtime mode; else read-only        |

- Agent tokens: 32 random bytes, hex, stored as SHA-256 per provider session; valid while used
  at least once in 24 h (`touch_thread` renews); revoked per thread or provider session; at
  most 1024. This is `McpSessionRegistry.ts`.
- **Differs from the T3 server.** There an outside caller needs an MCP OAuth client token
  (`/oauth/mcp/*`, approved with a pairing code that carries an access level), and an
  environment session is refused with 401. The Conn Server has no MCP OAuth. Orbit's planned
  Swamp driver authenticates with an `Orbit Swamp` session from `t3 auth session issue`, which
  the T3 server would refuse here; a session that may already drive threads over `/ws` gains
  nothing new on `/mcp`. Not served: `T3-Mode-Limit`, `T3-Sender-Thread`, linked environments.
- Write tools check the caller as `McpToolAccess.ts` does (`tools/mod.rs`, `writing_caller` and
  `writes_threads`). A read-only client is refused. A thread caller must still be live: its
  thread exists, is not archived, is on the credential's provider instance, and has an active
  run or a pending background subagent of that instance (`parent_not_active` otherwise). Every
  target thread other than the caller's own may not run in broader modes than the caller.
  `t3_thread_launch` takes the live check; `send`, `interrupt`, `update`, `organize`, the
  `respond` action of `t3_pending_request`, the write actions of `t3_queue` and a model change
  in `t3_thread_configure` take both; `delegate_task`, `task_status`, `task_cancel`,
  `send_to_user` and `t3_background_wait` act as the caller and take the live check. Reads take neither. The engine records no
  background tasks yet, so the background-subagent exception never applies today.
- 401 carries `www-authenticate: Bearer` and no `resource_metadata`, so no agent starts a sign-in.

## Tools

The T3 server registers 87 tools (`gen-tools.mjs --all`). Context filters: `tool_search` is listed
only to clients that send `t3-tool-exposure: deferred`; `t3_environment_link(s)`/`unlink` are
hidden while linked environments are off; `watch_pull_request`/`unwatch_pull_request` are hidden
from delegated children. Preview, device and panel tools are listed to everyone and fail without
the capability.

Served tool definitions come byte for byte from `apps/server`. Each served tool has
a unit test and `parity.mjs` steps.

Where they differ, because the engine does not do it yet:

- The pull request link tools (`tools/pull_requests.rs`) read a project's `repositoryIdentity`,
  which this engine does not resolve yet (T3's `RepositoryIdentityResolver`). A target named by
  `repository` and `number` without `host` therefore fails with "This thread's project has no
  recognised remote", where T3 uses the project's remote. URL targets and targets with a host
  answer as T3's.

- `t3_thread_send` maps its modes as `ThreadManagementService` does (`auto` steers a running
  turn, else starts; `queue`, `steer`, `restart`). `freshContext` starts a new provider session and never steers.
- `t3_thread_launch`: `root`, `existing_worktree` and `worktree` (the engine makes the worktree
  through the server's host before the thread exists; `parity.mjs` compares the result). No
  `scratch`, no attachments on launch (the three attachment tools are served). The thread
  is recorded as `createdBy: user` (the engine's `launch` sets it). Without `modelSelection`
  a client gets the first ready provider's first model.
- `t3_thread_wait` ends on `waiting` too, as Orbit's driver expects; no restart chains, since the
  engine ends a run on restart.
- `t3_thread_update`: `rename` only.
- `t3_thread_search` follows `searchThreads` (`ThreadSearch.ts`): title, branch and project hits
  among the project's active listed threads, then message hits from the engine's index (one per
  thread, outside the title hits), with a fifth of the slots kept for messages. Not ported:
  T3's title scoring (`scoreThreadSearch`) and message ranking (`rankMessageMatches`,
  `compareHits`). Ours orders titles by activity and takes each thread's newest message hit;
  T3 takes the best match, then the user's words. Parity compares titles and sources in order
  for three queries on one thread, so this gap is not covered there.
- `t3_thread_organize`: the own agent's settle mid-turn waits in the background for the run
  (`settleAfterRun`, 24 h, at most one wait per thread). It does not check T3's "a watch
  started after the request keeps the thread active".
- Delegation: `delegate_task` dispatches the engine's `delegated_task.request`, which makes the
  child (lineage `subagent`) and wakes the parent (`always`; `settled_only` for `mode: wait`,
  upgraded when the wait gives up). Task ids are `node:delegated-task:<commandId>`. No
  `isolation: worktree`: the engine's `delegated_task.request` takes no workspace strategy
  yet. No remote targets.
- `orchestrator_capabilities`: no option descriptors, favourites or model preferences.
- `send_to_user` stores nothing, as in T3: the provider records the call as a `dynamic_tool`
  item, and the client shows its `sentMessage`. Our engine sends tool items whole (no wire
  projection, no bounded history yet), so the item reaches the client with its output.
- Results keep the TS keys; serde_json sorts keys, so the `text` copy orders them differently.

A tool we do not serve is not listed: an unknown tool is `-32602 Tool 'x' not found`, as the T3
server answers a hidden one.

`tools.implemented` is the served set. `agent_texts_name_only_known_unserved_tools` checks
which unserved tools the agent instructions mention.

**`t3_background_wait`** (`tools/background.rs`; T3: `toolkits/orchestrator/handlers.ts`,
`ThreadManagementService.awaitBackgroundTasks`): `actsAsCaller`, so a live thread caller only.
`taskIds` holds 1 to 20 strings, each trimmed as JavaScript trims; a blank one is `-32602`
(`Expected a non-blank string` at its index). `waiting` defaults to `true`. The engine
(`Engine::await_background_tasks`) asks the live session of the caller's active provider
thread, with a 15 s limit; Claude marks (or clears) the ids on its roster and reports it, so
the thread stays Working. The answer is `{matched, unmatched}`: matched ids once each, the
others in the given order. Refusals, with T3's messages: no live session `orchestration_error`
(`unavailable`); a provider without a roster (Codex, Grok) `invalid_request`
(`unsupported`); marking that matches nothing `invalid_request` (`unmatched`); a provider
failure or timeout `orchestration_error` (`failed`). Clearing that matches nothing succeeds.

## The SDK or our own

Measured 2026-11-13 against `rmcp` 3.10.0, the official SDK (released 2026-11-12, 28 M recent
downloads; protocols 2024-11-05 to 2026-07-28; a tower `StreamableHttpService` that fits axum and
a one-thread runtime). Both builds serve the same handlers; only the transport differs (the SDK
build is commit `35cfdba72b`). macOS arm64, release profile, `ps` RSS and `footprint`:

| Build         | Binary  | Idle            | 1 session    | +100 sessions |
| ------------- | ------- | --------------- | ------------ | ------------- |
| Before `/mcp` | 5.02 MB | 4.8 MB / 2.0 MB | —            | —             |
| Ours          | 5.31 MB | 4.9 MB / 2.1 MB | 5.7 / 2.6 MB | 6.5 / 3.4 MB  |
| `rmcp`        | 6.24 MB | 5.2 MB / 2.0 MB | 7.5 / 3.8 MB | 18.8 / 15 MB  |

`rmcp` brings 29 crates of its own (futures, schemars, chrono, tracing, tokio-util, uuid, ...), 0.94 MB, and
about 0.12 MB per open session: each session runs a worker task with its own channels until 5
idle minutes pass. Agents keep a session per CLI process and Swamp may open one per step, so that
is the cost that grows. It also always answers over SSE. Ours is about 300 lines (`transport.rs`,
`sessions.rs`). We keep ours. Revisit when T3 moves to a protocol revision we do not serve;
`35cfdba72b` shows the SDK wiring.

## Agent wiring

`McpService::issue_thread_credential(ThreadCredentialRequest { thread_id, provider_instance_id,
subagent })` returns an `McpServerEntry { url, authorization, .. }` for one provider session:

- Claude: `entry.claude_server()` is the `mcpServers["t3-code"]` value (`type: http`, `url`,
  `headers.Authorization`, `timeout` 65 min); `entry.claude_mcp_config()` is the whole
  `--mcp-config` JSON. Pre-approve `mcp__t3-code__*` as the T3 adapter does.
- Codex: the provider writes `mcp_servers.t3-code` (wait tool disabled) and
  `mcp_servers.t3-code-direct` (only `t3_thread_wait`, out of code mode) into its thread
  config (`conn-provider-codex/src/launch.rs`).
- Call `revoke_provider_session` when the session ends and `touch_thread` when a turn starts.

`crates/conn-server/examples/mcp_agent.rs` proves it: it serves one thread and writes that
thread's `--mcp-config`, and `claude -p --model claude-haiku-5-5 --strict-mcp-config
--mcp-config <file>` listed threads, launched one and waited for it.


## Pull request watches and guides

`watch_pull_request` and `unwatch_pull_request` follow `PullRequestWatchService.setWatching`:
the writer checks, the thread, the target, the subagent and merged refusals, then an
uncached `summary` through the server's GitHub panel (`McpConfig::pull_requests`), then the
engine's `thread.pull-request.watch`. Only a `PullRequestUnavailableError` from the host
refuses the watch, with its message; other host failures leave the watch to recover. Both
tools are hidden from delegated children (`src/subagent-hidden.txt`).
`read_pull_request_guide` follows the toolkit's `locateAll`: the panel names the project that
checks out the repository (`locateProject`), and the stored guide comes from the panel's
`reviewGuide`. `write_pull_request_guides` is not served: the server has no review guide
generator, so the tool would always fail. The watch loop that wakes the thread is the
server's (`conn-server/src/methods/pull_requests/watches.rs`).

Nested array elements are type-checked field by field (`catalog::check_arguments`), as
Effect decodes `create_threads`' `threads`.

## HTML rendering

`html_render` publishes a finished page to the calling thread. It is hidden from outside
clients and checks that the caller still owns a live run. Plan mode may pass inline HTML;
only full-access threads may pass a file path. The files service prepares the page and saves
its attachment. The result is the normal client render reference and T3's success message.
No preview capability is advertised. `html_preview` and the browser tools remain unserved.

## Secret requests and panels

Secret-provider reference answers are not advertised. Browser URLs and tab ids fail with
`capability_denied`: they need the desktop preview relay and current-tab pinning, which are
not served. [conn-features](../conn-features/README.md#secret-requests-and-panels) lists the
secret and panel bounds that differ from T3.
`mcp_call` and `mcp_connect` go through the same panel broker, with T3's 90-second action
timeout.

## Test logins and database panel

`save_test_login` and `request_credentials` use the shared test-login store. They return
metadata only. They are hidden from outside clients; saving requires a live calling
thread, while listing also works after its run ends. Both require the session’s `preview`
capability, captured from global or project “Agent browser access” at session start.
`fill_credential` and the site credential RPCs remain unserved until the desktop preview relay exists.

`database_query` sends the SQL and connection name to the existing desktop panel broker,
waits up to 90 seconds, and returns the desktop's result with `shownOn`. The desktop owns
read-only enforcement, query limits and the 20-row preview, as in T3. The Linux server
opens no database connection and needs no database driver. No desktop means a clear error.
