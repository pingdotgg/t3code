T3 Code Fork Plan

A maintainable fork with a contained development setup and focused improvements to project navigation, long-thread retrieval, subagent inspection, and Bitbucket authentication.

Upstream-syncableContainer-firstLocal-state isolatedFour product goals

Goals and acceptance criteria

  1. Keep a repeatable path for bringing upstream changes into the personal fork without losing custom work.
  2. Run development in a container with its own dependencies, credential boundary, and T3 state. Do not use the normal T3 installation or live data.
  3. Make projects the sidebar's primary level; expand a project to find its threads, including projects with no active threads.
  4. Provide an at-a-glance index of user prompts inside a thread; selecting one jumps to the prompt and its response.
  5. Show parent agents and nested subagents with status in the Agents view. Selecting a child opens its own full inspection view, including attributable changes and diff when available.
  6. Use the existing bkt CLI login for Bitbucket API workflows, without a separate T3 Bitbucket credential. Keep Git transport authentication separate.
Checkout snapshot: this folder is currently on main, tracking origin/main; origin points to the official T3 repository and no personal fork remote exists yet. The stack is a TypeScript monorepo with Vite+, pnpm, Node 26, and some Rust/native tooling. There is no Python project manifest or uv.lock; Python files are utility/build scripts.

Phase 0 — establish the fork and upstream workflow

  1. Create a GitHub fork of pingdotgg/t3code under the intended account or organization.
  2. Set origin to the personal fork and add upstream for https://github.com/pingdotgg/t3code.git. Verify fetch/push URLs and tracking before any push.
  3. Keep local main aligned with upstream/main; make custom changes on named feature branches. Keep UI, subagent, and Bitbucket work in focused branches/commits.
  4. Sync routinely: fetch, inspect upstream changes, merge or rebase them into the fork integration branch, resolve conflicts, and run affected checks. Avoid force-pushing shared branches; record known-good integration points.
  5. Record the starting upstream SHA and verify a clean build/start in the isolated environment. Do not publish binaries or open an upstream PR unless separately requested.

Done when: remotes clearly separate personal fork from upstream, the sync routine is documented, and custom work is not done directly on upstream-tracking main.

Phase 1 — isolate the development environment

  1. Use the repository's Dev Container by default. It provisions Ubuntu, Node 26, Rust, Vite+ (vp), and the pnpm workspace dependencies. Dependency volumes stay in Docker; the host does not need the T3 toolchain globally.
  2. Before vp run dev, create a separate sanitized, ignored .env.local for this checkout. Keep production T3 Connect tokens, provider credentials, and other production secrets out of it; .env.local overrides .env. Also check inherited shell variables, which override repository env files.
  3. Keep runtime state under the checkout's ignored .t3 directory. Disable DB seeding for the first start (T3CODE_DEV_SEED=0 or --no-seed) so no personal data is copied. This only disables database seeding; it does not stop credentials from being loaded from .env, .env.local, inherited environment variables, or other configuration. Start with synthetic data and the free Replay (dev) provider.
  4. Keep .env, .env.local, credentials, and pairing URLs out of Git. Do not connect the dev server to production T3 Connect or production credentials by default. If credentials become necessary, use a separate test account and minimum scopes.
  5. Defer host-only Electron GUI and mobile native builds; begin with web/server development.
  6. Do not add uv merely to imitate a Python virtual environment. There is no current Python package/dependency project. If a maintained Python tool later gains external dependencies, give that tool its own pyproject.toml, uv.lock, and project-local .venv, or run it in the container. Keep Blender asset scripts tied to their documented Blender runtime.

Done when: a fresh container starts web/server T3 with state in .t3, requires no global Node/pnpm/vp on the host, uses a separate empty database on first start, and receives no production credentials.

Phase 2 — project-first sidebar

  1. Inspect sidebar code and project/thread query contracts; reuse existing grouping and ordering where possible.
  2. Make projects stable top-level rows. Expand/collapse each project for its threads. Define findable homes for pinned, archived, settled, snoozed, and no-project threads.
  3. Show projects even when they have no active threads; add counts/status where useful. Preserve keyboard navigation, search, responsive layouts, and existing actions.
  4. Keep the change presentational unless the server demonstrably lacks required metadata.

Acceptance: all configured projects are discoverable; expanding one reveals its threads; selecting a thread opens its conversation; empty/archived projects and no-project threads have intentional access paths; wide and narrow layouts work.

Phase 3 — prompt index inside a thread

  1. Reuse message history, search, and timeline/minimap data. Build a compact outline of user-authored prompts with a readable preview and optional time/order.
  2. Selecting a prompt scrolls to the user message and its corresponding assistant answer. Handle long prompts, attachments, queued/steered messages, and multiple assistant/tool messages without listing tools as prompts.
  3. Make the outline easy to open and dismiss without permanently taking chat space. Preserve keyboard and mobile usability. Choose side panel, popover, or minimap extension after inspecting the UI.
  4. Keep search for known keywords; the index is for scanning prior questions, especially advice-only threads.

Acceptance: long threads expose scannable user prompts; choosing one reliably lands at the prompt/answer pair; navigation state is predictable; no schema/server change unless data gaps require it.

Phase 4 — Agents tree and full subagent inspection

  1. Trace Agents-view lineage, status, and activity data. Identify provider capability differences before changing the UI.
  2. Add expandable parent rows with nested subagents and clear live/terminal statuses. Avoid duplicating expanded children as peers; keep a way to locate a child directly.
  3. Selecting a child opens its own inspection view: prompt/task, messages, tool/activity timeline, status, files, and diff where attributable.
  4. Keep controls accurate: stop/cancel targets the selected execution. If a child cannot accept messages, direct the user back to its parent instead of showing a misleading composer.
  5. Check whether checkpoints/worktrees provide child-level changes. If a child shares a checkout or a provider does not report separate changes, do not present the parent's aggregate diff as the child's work. Determine whether server attribution/checkpoints need extension.

Acceptance: hierarchy/status are clear at a glance; a child is one click away; attributable changes show when supported; unsupported attribution is explicit; lifecycle controls stay correct.

Phase 5 — Bitbucket through bkt

  1. Audit packages/source-control-bitbucket and the source-control contract: repo/PR listing, create/update, reviews/comments/status, identity checks, pagination, Cloud/DC, and errors. Map each operation to a supported bkt command/output.
  2. Add a CLI-backed adapter on the T3 server environment. Use bkt's existing auth/keyring/context; never copy raw credentials into T3's secret store or logs. Detect executable/version/host/context/auth and explain missing setup in Settings.
  3. Keep Git transport separate: bkt API auth does not itself configure SSH/HTTPS clone, fetch, or push. Preserve normal Git credential-helper/SSH behavior.
  4. Match existing Bitbucket capabilities where supported; report unsupported actions instead of silently reverting to the old token flow. Confirm Cloud scope; include Data Center only if needed.
  5. Add executable-path configuration only if discovery requires it. The CLI path must not require Premium-only token setup in T3.

Acceptance: an already-authenticated bkt user can use supported T3 Bitbucket workflows without entering a token into T3; credentials remain in bkt storage; errors are actionable; Git continues to use its own credentials; no unsafe fallback exists.

Phase 6 — integration, verification, and maintenance

  1. Integrate focused branches into the fork as each feature is reviewable. Sync upstream routinely instead of allowing long divergence.
  2. Use focused checks for changed areas, not repo-wide checks unless requested. Review web changes in an integrated client. Use synthetic data and Replay; use a dedicated Bitbucket test repo/context for API verification.
  3. Capture before/after evidence for sidebar, prompt index, and Agents view. Document provider limits and the bkt version/commands used.
  4. Update user docs after behavior/settings settle. Keep fork-specific planning separate from upstream product docs.

Release gate: fresh-container setup works; all four product goals meet acceptance criteria; scoped checks pass; no live userdata, credentials, repositories, or Bitbucket projects were changed; upstream sync has been tested.

Dependencies and assumptions

  • Phase 0 comes before code changes; Phase 1 comes before running/testing the fork.
  • Phases 2 and 3 are mainly independent web/client navigation work.
  • Phase 4 depends on confirming lineage and child-diff attribution before choosing UI versus server scope.
  • Phase 5 starts with an API/CLI capability map and keeps Git transport distinct.
  • Assume Bitbucket Cloud because the user has working free-plan bkt auth; confirm if Data Center is also in scope.
  • Prompt index lists user messages and navigates to each prompt's associated answer.
  • Subagent inspection aims for top-level richness but preserves truthful child-level attribution; provider limits may prevent a per-child diff.
  • This is a personal fork first. Upstream PRs, publishing builds, production connections, and writes to real Bitbucket repos are out of scope unless requested later.
