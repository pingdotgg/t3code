# Credential storage and review

Hyakki can encrypt its local server vault on Linux. Each record uses AES-256-GCM with its own nonce and is authenticated against its record name. The key is kept in the Linux Secret Service keyring, not in the vault directory or a Hyakki backup. An activated vault will not open without that key. Other installations and platforms still use the original private file store until migrated or supported. The 1Password provider stores references and reads values on demand.

To activate the Linux vault, first update Hyakki and stop the desktop, CLI and any background service using the home. From the repo run `node scripts/enable-local-vault.mjs ~/.hyakki`. Activation requires an unlocked keyring and `secret-tool`. Start the updated build afterward. Do not start an older build with that home. Keep the OS keyring backed up securely: losing its vault key makes old vault files unrecoverable. A moved home also needs its original key associated with the new path.

Migration replaces the existing files without creating a plaintext backup, but does not erase previous backups, filesystem snapshots, or SSD remnants. Rotate credentials if older copies were exposed. The server holds the key while it runs, so locking the keyring alone does not relock an already running server. Full-access processes running as the same OS user are outside this protection. A credential explicitly provided to an agent shell through a temporary file remains readable to the OS user that runs the shell.

Changes to credential handling, authentication, and review policy need the approval of the GitHub code owner. The PR notification reads file paths and does not run or check out PR code. Branch protection, not the notification, enforces approval. A code owner cannot approve their own pull request. A repository or organization administrator who can edit branch protection can still change the policy itself.

## Typed local entries and approvals

The local vault has API tokens, website logins, and secure notes. Values are encrypted in `vault-entry-<id>` records. New entries use opaque random IDs; names and website metadata are returned only through a settings-authorized list request. The list never returns protected fields. Creating, editing, or deleting credentials requires both settings-write and provider-management scopes, because tokens can supply running providers. Edits with blank protected fields retain their previous values. Per-process serialization prevents a concurrent edit from resurrecting a deleted entry. Clients require the server's `localVaultEntries` capability before offering structured writes.

The reserved `hyakki-vault` settings source resolves only token fields, server-side and without a second plaintext cache. Login and note fields cannot become provider token references. A provider may retain a previously applied token in its process environment until refreshed or restarted.

A vault answer to an agent request requires task operation and provider-management scopes. Only the chosen fields are copied into the existing project-bound, expiring, one-use credential broker. The thread records request status, not the credential values. Login approval requires an exact HTTPS origin match, including port and subdomain; that origin is also stored with the broker record and checked when a protected consumer supplies its actual target. Consumers without a target cannot consume a login reference.

File delivery is explicitly different: the approval card says that the agent's commands can read the fields, and the file is created owner-only. A saved website is not a sandbox for commands after that handoff. File delivery can be retried against the original approved request, and files expire under the existing 24-hour policy. Deleting a vault entry does not revoke a token at its issuer, invalidate previously delivered credentials, or erase an already-approved broker copy.

Storing a token, login or note grants no service access by itself. Service credentials bind an account to one of Hyakki's implemented read operations. For GitHub.com, GitLab.com and Slack, the backend checks the token at the provider's fixed endpoint before saving it. A service token is not a generic provider reference or a command-file source. Gmail uses an owner-supplied OAuth client and a separate Google grant. Every private service read needs a fresh approval; neither the secret nor the returned rows are sent to the model.

## PIN and disclosure controls

The local vault now defaults to ask-first, with a 6 to 8 digit PIN for writes and credential approval. Protected-use grants do not grant plaintext disclosure. Command-file access needs explicit consent and fresh PIN verification even for an allow-mode entry. PIN failures persist across restarts, and policy changes invalidate pending vault approvals. See [the access-control contract and tests](vault-access-control.md). This is an application-level guard, not isolation from same-user full-access agents.

## Register a Google client for a vault entry

Hyakki does not ship a Google OAuth client or load a shared client ID or secret from the environment. Each Gmail connection uses the owner's **Web application** registration, including on the native desktop.

1. On the host, open **Settings → Secrets → Add credential → Gmail** and copy the **OAuth redirect URL**. Use the advertised loopback URL on the host itself; a remote browser's loopback is not the server. For remote setup, set `HYAKKI_GMAIL_REDIRECT_URI` on the server to the exact HTTPS URL ending in `/oauth/gmail/callback`, and route that path to the same environment. A LAN-only listener needs this explicit HTTPS callback even for local setup. Hyakki does not infer a public URL from request headers or the browser. If the callback has a different origin from the connection, its public origin must also serve that environment's `/.well-known/t3/environment` descriptor.
2. In **your own** [Google Cloud project](https://console.cloud.google.com/apis/library/gmail.googleapis.com), enable the Gmail API and configure the OAuth consent screen. For a new app used only by its creator, [Personal mode](https://support.google.com/cloud/answer/15544987#zippy=%2Cquick-setup-for-personal-use-personal-mode) creates a client without test users or seven-day test expiry; existing External or Internal projects cannot switch to Personal. If the project is **External → Testing**, open [Google Auth Platform → Audience](https://console.cloud.google.com/auth/audience) in that same project. Under **Test users → Add users**, enter the exact Gmail address you will sign in with and save. Google’s “only be accessed by developer-approved testers” message means to check this list. [Test grants for Gmail expire after seven days.](https://support.google.com/cloud/answer/15549945#publishing-status)
3. Under **Google Auth Platform → Clients**, create a **Web application** client. Paste the exact URL into **Authorized redirect URIs**, not **Authorized JavaScript origins**. If the host's port or public origin changes, update Google's registration and the saved connection to match.
4. Enter the client ID and secret **in the vault editor only**, and save with your vault PIN. Choose **Continue to Google**, grant consent in your browser, then return to Hyakki and enter your PIN to **Finish connection**. If the callback says the attempt expired, was already used, or was replaced, choose **Restart Google sign-in** in Hyakki and complete only the newest Google window. Successful consent uses only [Gmail read-only access](https://developers.google.com/workspace/gmail/api/auth/scopes); broader scopes are not accepted. A provider process never needs these credentials. See [using a connected service in chat](../user/secrets.md#connect-a-service).

Changing the registration invalidates its old grant and outstanding approvals. An entry previously connected through a host- or publisher-managed client must be reconnected. Disconnect removes the local Google grant but keeps the client registration; delete the entry to remove both, and revoke consent separately in the Google Account. Do not recover a legacy grant by trying a different owner's client.

Proton Pass vault references are separate from account connections. A connector should support a dedicated scoped CLI session, read only the requested fields, never put secret values in arguments or logs, and fail closed if the session is unavailable.

## Reference implementations

- In self-hosted [n8n's Google OAuth setup](https://docs.n8n.io/integrations/builtin/credentials/google/oauth-single-service/), the user supplies the Web client and registers the callback shown in the editor. The [Gmail node](https://github.com/n8n-io/n8n/blob/5de543b001de93f1bb0169aa52c3a96236605025/packages/nodes-base/nodes/Google/Gmail/v2/GmailV2.node.ts) is available as an agent tool; [credential encryption](https://github.com/n8n-io/n8n/blob/5de543b001de93f1bb0169aa52c3a96236605025/packages/core/src/credentials.ts) and [human review](https://docs.n8n.io/advanced-ai/human-in-the-loop-tools/) are separate. Hyakki follows that separation, not n8n's broader Gmail scopes or general-purpose HTTP access. Its read tool has fixed Google destinations and requires private approval on every use.
- [Pots / pi-durable-bot](https://github.com/Crokily/pi-durable-bot/blob/main/src/core/secrets.ts) reads configured secret files and masks known values before tool output reaches the model. Masking is useful defense in depth, not encryption at rest.
- [Paperclip](https://github.com/paperclipai/paperclip/blob/master/docs/deploy/secrets.md) encrypts local secret versions with AES-GCM. Its master key comes from an environment variable or a private key file. Users bind secret references to workloads; Paperclip resolves them server-side and injects real values at execution time. The board does not receive plaintext, but the consuming process can read it. Log masking is best-effort.
- [Nod](https://github.com/n8n-io/nod/blob/main/docs/src/content/docs/trust/vault.mdx) binds AES-GCM records to their owner, identity and purpose, keeps the key outside the database, and privately uses secrets without passing them to the model. Its documented key source varies by deployment; Linux can use a private key file.
- [OpenBot](https://github.com/nightly-labs/openbot/blob/main/src/main/secret-storage-cipher.ts) uses Electron safe storage where available and can fall back to an AES-GCM key file on Linux or macOS. Its [vault store](https://github.com/nightly-labs/openbot/blob/main/src/main/vault-store.ts) writes the encrypted envelope atomically. Hyakki deliberately does not use that key-file fallback.
