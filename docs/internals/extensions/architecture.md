# Extension architecture: V1 views and trusted environment packages

## Decision

Build on orchestration V1 first. Keep one public extension SDK whose identities and presentation contracts do not expose either orchestration engine. Adapt existing domain services and client surfaces through narrow host-owned interfaces. The first environment package exposes workspace reads and uses the existing provider MCP transport. A later V2 integration should reuse the SDK and implement engine-specific bindings, with semantic compatibility tests rather than renamed V1 commands.

The implemented SDK is trusted, in-process code. It supplies bounded serializable records, view lifecycle, optional React rendering, captured composer context and read-only message cards. Bundled integrations register directly; trusted environment packages add installation, supervised server execution, authenticated client loading and provider MCP tool delivery. This is not an untrusted-code sandbox. See [environment package ownership](./environment-packages.md). See the [developer preview](./developer-preview.md), [placement rules](./placements.md) and [SDK guide](../../../packages/extension-sdk/README.md).

## Ownership, identity and authority

A **resource** is the domain object: a PTY, browser session, repository, issue or device. A **viewer** is one presentation of that resource. The environment/domain service owns resource lifetime. The client shell owns placement, focus, ordering, visibility and saved viewer records. Core continues to own thread identity, authentication, approvals, provider lifecycle, event persistence, checkpoint ordering and turn settlement.

Resource identity includes namespace, resource ID and applicable environment/project/thread scope. Use `resourceKey`, never a bare path or thread ID. Viewer identity additionally includes its layout scope, placement and opening generation. Two threads—or two placements—can have separate viewers of one project resource. Opening both placements creates independent viewers; it is not a promise of shared React state or a cross-container move. [Layout storage](../../../apps/web/src/rightPanelStore.ts) validates records and captures generation when saving, so a delayed save cannot reopen a closed viewer or overwrite its replacement.

Hide preserves an already-active generic viewer and its unsaved presentation while disabling SDK activity. Show resumes it. Cold hidden restored records do not activate, and closing the retained viewer while hidden does not activate its successor. Switching selected tabs or thread boundaries can dispose and restore from saved state. Close/disable/context replacement abort the viewer lifetime and dispose its controller; they must not terminate a borrowed PTY, close an unrelated browser resource or stop a user-owned simulator. Explicit domain termination remains a separate host action. The [side-panel retention hook](../../../apps/web/src/extensions/useRetainedExtensionSidePanel.ts) and [extension dock](../../../apps/web/src/extensions/GenericExtensionDock.tsx) preserve those distinct boundaries; hidden chrome is inert.

Services bind invocation to a copied context and check declared capabilities plus the supplied authorization callback on every call. Context shape validation does not authenticate project membership. The host adapter must resolve the actual environment/project and retain backend authorization and containment checks. The [workspace reader](../../../packages/extension-sdk/examples/workspace-reader/README.md) demonstrates that boundary without exposing arbitrary RPC dispatch. Credentials, database handles, unrestricted filesystem access and provider/process control are not portable service contracts. Trusted in-process code can bypass an SDK convention; permissions are not an OS sandbox.

## Immutable context and bounded presentation

The draft prompt string remains the source of truth. Selection captures bounded text, title, optional source URL, originating scope, contribution/package identity and capture time. The normal send path freezes that string before asynchronous work and uses existing admission commands. This is **capture on selection**, not a live read at server admission. Explicit reselection creates a new snapshot. The [composer contribution UI](../../../apps/web/src/extensions/ComposerExtensionContext.tsx), [core editor](../../../apps/web/src/components/ComposerPromptEditor.tsx) and [timeline](../../../apps/web/src/components/chat/MessagesTimeline.tsx) derive their presentation from the retained text.

Known blocks display readable title/source/content; copy/export preserve source and attribution. Existing draft recovery, stash and recall retain the same string after unregister. Retry or fork paths that reuse the original message text retain that snapshot; they must not silently refresh external data or clone live jobs. Historical paging decorates only the source item actually loaded. Future structured attachments need explicit source-item identity and migration tests; present text fallback does not prove an unknown attachment type works across clients.

Limits are part of the preview contract: eight contexts per prompt, 8 KiB text per selection, 32 KiB serialized context total; four message cards and sixteen compatible projector invocations per visible row. Hosts with no compatible message decorators are skipped before copying payloads. Registration is bounded, errors are isolated, and original messages survive decorator failure. View publication keeps one bounded latest snapshot with monotonic generation-local sequence numbers; stale/hidden publications and stale service results are rejected. Cancellation bounds owned activity but cannot undo a completed external effect or preempt arbitrary synchronous trusted code. See [host contracts and tests](../../../packages/extension-sdk/test/host.test.mjs).

## Compatibility and V2

Keep SDK API major, package semver, restoration schema, layout storage and orchestration wire versions separate. The preview accepts API major 1 and exact restoration-version matches; it supplies no automatic state migrator. Unknown/uninstalled/incompatible views retain their saved record and readable fallback. Installed-package discovery is environment-scoped. Automatic upgrades and broader compatibility negotiation require additional implementation.

Web and desktop share the current React host. React Native mobile needs its own contribution renderer and host integration. Existing message text remains available through their ordinary message paths, including the source envelope; the new readable formatting, chips and cards are not implemented there. A future wire schema change must update the mobile client explicitly. Local, remote, relay and tunnel transport correctness remains the domain adapter responsibility; serializable SDK types alone add no transport endpoint or all-client guarantee.

The V2 assessment inspected [PR #2829](https://github.com/pingdotgg/t3code/pull/2829) at [`7dd9873`](https://github.com/pingdotgg/t3code/tree/7dd9873ed0874ad5807db4875bc7c2575978821f). These are pinned research findings, not assertions about its current head:

- V2 logical runs, attempts, nodes and message/item records do not map mechanically to V1 turns. Keep any future execution reference opaque and optional for historical content. The [V1 importer](https://github.com/pingdotgg/t3code/blob/7dd9873ed0874ad5807db4875bc7c2575978821f/apps/server/src/orchestration-v2/LegacyV1ThreadImporter.ts#L223) preserves message IDs without manufacturing run/node ownership.
- Admission receipts still differ from completed external operations. Provider tool delivery, session rotation, steering, approvals and rollback need distinct adapter semantics. Keep approval responses and checkpoint coordination in core; do not expose raw engine commands.
- Replay cursors and history windows need scoped reset/resnapshot handling. Rebuilding projections must never replay external writes. V2 import and fork must preserve attribution even where no execution mapping exists.
- One SDK does not imply one current client can connect to both engines. The pinned [compatibility boundary](https://github.com/pingdotgg/t3code/blob/7dd9873ed0874ad5807db4875bc7c2575978821f/packages/client-runtime/src/connection/compatibility.ts#L9) remains engine-sensitive. Prove separate adapters before claiming mixed-engine support.

## Reference packages and next delivery

The implemented source examples are the [public counter](../../../packages/extension-sdk/examples/counter/counter.ts), [installable workspace reader](../../../packages/extension-sdk/examples/installable-workspace-reader/README.md), bootstrap workspace reader and [issue-context fixture](../../../packages/extension-sdk/examples/issue-context/issue-context.mjs). The last contains explicitly static issue data; it is not an installed tracker backend.

Use the device and issue research as domain-adapter precedents, not as completed extension migrations. [Device PR #10677](https://github.com/pingdotgg/t3code/pull/10677), inspected at [`834988b`](https://github.com/pingdotgg/t3code/blob/834988b6a93ca9672058b6de125fc3b44186c6a4/apps/server/src/device/DeviceHost.ts), separates viewing, agent control and user-owned devices. A real simulator package still needs lazy host setup, authenticated media, screenshot artifacts and independently revocable input authority. Closing a viewer must not terminate the simulator.

[Issue PR #6315](https://github.com/pingdotgg/t3code/pull/6315), inspected at [`0a2a90b`](https://github.com/pingdotgg/t3code/blob/0a2a90b7b543a2cac074311c2baff54f60498400/apps/server/src/issue/IssueProvider.ts), supplies a domain adapter precedent. Keep the shared issue workspace separate from tracker implementations; resolve opaque tracker/account/source identity and pagination explicitly. Attaching issue context must not grant permission to comment or close an issue.

Non-Git support is a third axis: [VCS drivers](../../../apps/server/src/vcs/VcsDriver.ts), [forge providers](../../../apps/server/src/sourceControl/SourceControlProvider.ts) and issue adapters are different contracts. Begin with detection/files/status/diff. The [checkpoint store](../../../apps/server/src/checkpointing/CheckpointStore.ts) still has Git-shaped eligibility; a generic viewer or registered driver does not establish non-Git checkpoint/worktree parity. Capture/restore/retention and failure ordering need independent proofs before enabling them.

The [pinned Pi extension documentation](https://github.com/earendil-works/pi/blob/6160683a4a8012f0d1cd30c145df18b4ca6f5176/packages/coding-agent/docs/extensions.md) is a useful precedent for separating tools and presentation. T3 wraps independent provider CLIs, so it cannot assume equivalent control over their model loops.

Next, implement only the narrow environment services required by one real device or issue package. Extend the authenticated MCP tool bridge with concrete domain capabilities rather than assuming control of a provider's model loop. Then prove cancellation, reconnect, immutable history and native fallback against both engine adapters. Trusted local installation is implemented; untrusted isolation, generalized orchestration control and arbitrary attachment schemas remain separate decisions. Contract tests, actual client journeys and comparative performance measurements are complementary evidence; none substitutes for the others.
