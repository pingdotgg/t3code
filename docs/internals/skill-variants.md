# Skill variants

T3 Code resolves a skill policy for each provider turn. Rules target a skill globally, by provider,
or by provider and model; the most specific enabled rule wins. The contracts and persisted model live
in [skillEvals.ts](../../packages/contracts/src/skillEvals.ts), and resolution lives in
[SkillVariantService](../../apps/server/src/skills/SkillVariantService.ts).

## State ownership

Variant bodies and their revision history belong to the environment's T3 state, not to provider
frontmatter or user skill directories. Tested provider harnesses ignore unknown model allow/deny
frontmatter, and their native controls have different scopes and semantics. Keeping policy in T3
makes precedence, reversibility, eval revision pinning, and remote clients consistent without
rewriting a user's skills.

Resolution is read-only. It computes a content hash and deterministic path under T3 state;
[turn preparation](../../apps/server/src/skills/SkillTurnPreparation.ts) materializes the exact
revision immediately before provider delivery. Content-addressed files are immutable, so a recorded
turn or eval arm continues to identify the body it used.

## Delivery and gating

`skillVariantDelivery` says where the directive is delivered. `skillGating` separately says whether
the provider harness enforces the policy (`native`), the model is only instructed (`instruction`),
or the policy cannot be delivered (`none`). The distinction is part of the
[adapter capability contract](../../packages/contracts/src/orchestrationV2.ts); a directive is never
reported as a hard gate.

## Context contamination

A native gate can prevent a future activation, but it cannot erase skill text already disclosed in a
native conversation. When the target policy omits an activated skill or changes its body,
[ProviderSwitchService](../../apps/server/src/orchestration-v2/ProviderSwitchService.ts) identifies
the contaminated paths using [skillContextContamination.ts](../../apps/server/src/skills/skillContextContamination.ts).
Only a non-empty omission set changes normal switch behavior: orchestration creates a fresh native
thread and [ContextHandoffService](../../apps/server/src/orchestration-v2/ContextHandoffService.ts)
filters those paths and related structured tool payloads from the handoff.

Sanitization is intentionally evidence-based and bounded. It can remove known skill files, variant
files, and structured activation results; it cannot reliably recognize every prose paraphrase of a
skill body. That remains a known gap, so a sanitized handoff is a stronger boundary than an
instruction but not a general semantic redaction system.

## Evaluation methodology

[SkillEvalService](../../apps/server/src/skills/SkillEvalService.ts) compares arms in isolated
worktrees. Each run freezes its task prompts, rubrics, expectations, prompt types, and resolved base
commits before launching work. A task is the independent statistical unit: repeats and judge samples
improve the estimate for that task but do not inflate the sample size. Arm outcomes are paired within
each task, and each comparison is judged in both presentation orders before positional labels are
mapped back to control and treatment. Position-flipped pairs contribute neutral preference and rubric
values. The order handling is isolated in
[skillEvalJudge.ts](../../apps/server/src/skills/skillEvalJudge.ts).

Judges use a positive allowlist: a Fable-family slug on the Claude driver or the exact
`gpt-5.6-sol` slug. The selected judge is explicit in every result, and usage limits fail the judge
operation rather than silently substituting another model.

[skillEvalStats.ts](../../apps/server/src/skills/skillEvalStats.ts) uses `MPID = 0.10` as the minimum
practically important net-preference effect. Fewer than 50 independent tasks retain their estimate and
confidence interval but cannot receive a verdict. A directional verdict also requires at least three
repeats and three judge samples; lower-count runs remain visible with a `too-few-repeats` reason. Runs
with 50–99 tasks require an absolute effect of at least `2 × MPID` and a Holm-adjusted interval
excluding zero; runs with at least 100 tasks use the standard `MPID` gate. This prevents repeats of one
prompt from looking like independent evidence and keeps statistically detectable but operationally
negligible changes from being called helpful or harmful. Prompt-type slices are exploratory estimates and intervals only. Overall confidence
intervals, paired effects, position consistency, completion rates, and multiple-comparison adjustment
remain visible so a controlled verdict is not read without its uncertainty.

Real-turn activation, completion, revert, token, cost, and tool-failure summaries are observational.
They are useful for finding where to evaluate, but model choice, task mix, and user behavior confound
them; they never produce a controlled verdict. Usage evidence and finalization live in
[SkillUsageService](../../apps/server/src/skills/SkillUsageService.ts).
