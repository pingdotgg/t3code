Project-scoped skills for the active chat

The $ skill picker must only show skills that are in scope for the project and branch (worktree) behind the current chat — not a union of every open workspace on the environment.

Implemented (tagged sourceCwd + client filter) Branch: fix/project-scoped-provider-skills See providers.md

Current status

Fixed via tagged inventory + client filter. The server still discovers across registered projects/worktrees (so project skills are not limited to process cwd), but each project skill is stamped with sourceCwd. Clients filter with filterProviderSkillsForWorkspace using worktreePath ?? project.workspaceRoot. A later scoped RPC remains optional for wire-size if inventories grow large.

Why the UI bleeds skills across chats

1 · Server probe
Provider status checks call resolveSkillWorkspaceCwds → every project + worktree.
2 · Contract
Results are flattened into ServerProvider.skills (environment-global, per provider instance). No project / cwd provenance on the wire for clients to filter.
3 · Composer
Web (and mobile chips) use activeProviderStatus?.skills / selectedProviderStatus?.skills for the $ picker — independent of the active project target.
Meanwhile · Agent turn
Turns already run with the thread’s effective cwd (worktreePath ?? workspaceRoot). The agent loads the right skills; the picker lies.

Goal

For a chat on project P with branch/worktree W, the skill inventory is:

  • User / global skills — always in scope for that provider.
  • Project skills discoverable from the chat’s effective workspace cwd only: thread.worktreePath ?? project.workspaceRoot, using each harness’s normal ancestor walk to the git root.

Out of scope for that chat:

  • Other projects’ workspaceRoots
  • Other threads’ worktrees / branches
  • Server process cwd, unless it is the same path as the chat’s workspace

Non-goals

  • Changing how provider CLIs load skills at turn runtime (already cwd-correct).
  • A new skill authoring format — keep each harness’s existing roots.
  • Merging skill implementations across providers; only the picker inventory is in play.
  • Remote-only special cases — same contract for local, Tailscale, and Connect (cwd is environment-local).
Branch ≈ worktree. T3 already models “this chat’s checkout” as thread.worktreePath when present, else the project root. That is the same resolution useActiveProjectTarget uses for file picker and content search.

Scope model

effectiveSkillCwd(thread, project) =
  thread.worktreePath?.trim()
  ?? project.workspaceRoot.trim()

inScopeSkills(providerInstance, thread, project) =
  userSkills(providerInstance)
  ∪ discoverProjectSkills(providerInstance, effectiveSkillCwd)

// harness-specific roots under a single cwd, not a cwd list
// examples:
//   Claude:  ~/.claude/skills + <cwd…gitRoot>/.claude/skills
//   Codex:   skills/list { cwds: [effectiveSkillCwd] }
//   Grok:    ~/.{claude,agents,grok}/skills + project .claude/.grok
//   Cursor:  harness project roots under that cwd
//   OpenCode: .opencode + .agents under that hierarchy

Collision rules (unchanged intent)

  • Within one cwd hierarchy: later / more-specific roots win (existing discoverSkillsFromRoots later-wins map).
  • User vs project: project wins when names collide (already encoded by listing user roots first).
  • Cross-project collisions must not appear in the same picker list — they were an artifact of the union.

Recommended design

Keep provider status lean. Stop stuffing every workspace’s project skills into ServerProvider.skills. Resolve project skills for the active chat cwd, the same way file search already keys off useActiveProjectTarget.

Recommended: split inventory into user skills on the provider snapshot + project skills keyed by workspace cwd, resolved server-side for a single cwd and cached. Client composes the list when the active project target changes.

Why not “just filter on the client”?

A pure client filter needs reliable provenance on every skill (which workspace produced it). Today names collide and paths are flattened. You could tag skills with sourceCwd and still ship the full union on every provider snapshot — that works, but it keeps paying for multi-workspace discovery and a large websocket payload on every provider refresh. Per AGENTS.md performance rules, prefer not to send every project’s skills to every client on every probe.

API shape

Preferred · scoped list + cache

  • ServerProvider.skills → user-scoped only (or empty for drivers that have no user skills).
  • New RPC (or filesystem-style project method): provider.listSkills with { instanceId, cwd } (or projectId + optional worktreePath; server resolves cwd).
  • Server cache key: (environment, instanceId, resolvedCwd, driverKind).
  • Client: userSkills ∪ projectSkills(cwd) when building the $ menu.

Fallback · tagged snapshot bags

  • Keep one provider snapshot, but structure skills as { user, byCwd: Record<cwd, skills> }.
  • Client picks user + byCwd[activeCwd].
  • Acceptable if RPC surface freeze is hard; still discover per-cwd without flattening. Heavier on the wire.

Server changes

  1. Retire “all workspaces” as the default probe path. resolveSkillWorkspaceCwds either becomes resolveSkillWorkspaceCwd(thread|project) (singular) or is only used by a maintenance/debug path. Provider status probes must not union all projects.
  2. Single-cwd discovery entrypoints for each driver (already mostly take cwd: string | string[] — call with one path):
    • discoverClaudeSkills(config, cwd)
    • discoverGrokSkills(cwd)
    • discoverOpenCodeSkills(cwd)
    • discoverCursorSkills(cwd)
    • Codex: skills/list with cwds: [cwd] only
  3. Split user vs project in discovery results so the provider snapshot can keep user skills without project bleed. If a harness cannot separate them cleanly, return the full single-cwd list from the scoped API and leave ServerProvider.skills empty for project entries.
  4. Codex merge helper. parseCodexSkillsListResponse today flattens multi-cwd responses and lets later workspaces win. Scoped path only ever passes one cwd; update tests that encode multi-workspace merge as desired picker behavior.
  5. Invalidation. Reuse / add skill file watchers per cwd when available (Codex already documents skills/* invalidation). Also invalidate when a worktree is created/removed or a project is deleted. Do not refetch every project on every probe.

Client changes

  1. Web composer (ChatComposer, ChatView, prompt editor plugins): skills prop = userSkills(selectedInstance) ∪ projectSkills(activeCwd).
  2. Active cwd: reuse useActiveProjectTarget().cwd (worktreePath ?? workspaceRoot). Draft threads and new-thread flow must resolve the same way as file picker.
  3. Switching chats: when environmentId / projectId / worktreePath changes, swap the project skill bag (cache hit preferred; no full provider re-probe).
  4. Mobile: same composition for native composer chips and any $ trigger surfaces. Hit every entry point that currently takes skills from provider status.
  5. Historical messages: chip rendering for past $skill mentions should keep working from message text + known names; do not drop labels when the user navigates to another project. Prefer name/displayName maps that can fall back to the raw skill name.

Contract notes

  • Optional provenance field on ServerProviderSkill is useful either way: sourceCwd and/or keep existing scope (user | project | harness-specific).
  • If adding RPC: put it next to other environment filesystem / provider methods in packages/contracts + rpc.ts; server handler resolves instance → driver discovery with a single cwd.
  • Backward compatible decode: older clients ignore new fields; older servers without scoped list leave clients with user-only or empty project skills (degrade gracefully, do not show other projects’ skills).

Risks

  • Draft threads without project — no cwd → show user skills only (or empty project bag), never the global union.
  • Custom provider instances — key cache by instanceId, not driver kind.
  • Name-only skill mentions in history — do not require the skill to still be in the active bag to render a chip label.
  • Performance — N projects must not mean N× discovery on every provider probe. Lazy load active cwd; optional warm cache for recently used threads.
  • Regression of “I can’t see any project skills” — first commit fixed empty lists when server cwd ≠ project root; scoped design must still use the thread cwd, not process cwd.
