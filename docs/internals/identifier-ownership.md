# T3 and Auldric identifier ownership

> Canonical identifier decision for the T3-authoritative Auldrics repository. This document owns
> classification and compatibility rules; it does not authorize a repository-wide rename or the UI
> implementation owned by the Marketing workspace issues.

## Decision

T3 owns Dev and all shared runtime identity. Auldric owns only the explicitly entered
Marketing/Strategy domain, its customer-facing objects, and a bounded distribution profile when an
Auldric build is packaged separately.

Brand follows the capability being used, not the company distributing the binary:

- a native coding session is **T3 Code**, including its shell, settings, providers, preview,
  pairing, updates, diagnostics, persistence, protocols, and agent self-context;
- an explicitly entered Marketing/Strategy workspace is **Auldric**, including its sources,
  workflows, artifacts, evidence, decisions, and reviews;
- a separately packaged Auldric application may use Auldric bundle and launch identifiers, but the
  embedded T3 runtime keeps its package, wire, storage-layout, configuration-variable, tool, and
  protocol-contract names.

Missing, disabled, or unknown product-domain state resolves to native T3 Dev. Visible branding is
never permission to change a compatibility identifier.

## Repository ground truth

The matrix below was checked against the current implementations rather than inferred from product
copy:

- web branding and browser storage: `apps/web/index.html`, `apps/web/src/branding.ts`, and the
  `*Store.ts` modules under `apps/web/src`;
- desktop identity, state, renderer scheme, packaging, and updater:
  `apps/desktop/src/app/DesktopEnvironment.ts`, `apps/desktop/src/app/DesktopStatePaths.ts`,
  `apps/desktop/src/electron/ElectronProtocol.ts`, and `scripts/build-desktop-artifact.ts`;
- mobile bundle, scheme, native modules, storage, and OTA configuration:
  `apps/mobile/app.config.ts`, `apps/mobile/eas.json`, `apps/mobile/modules`, and
  `apps/mobile/src/persistence`;
- server, contracts, provider context, tools, and persistence: `apps/server/src/config.ts`,
  `apps/server/src/provider`, `packages/contracts`, and `packages/client-runtime`;
- public T3, hosted-app, Connect, pairing, signing, and release configuration: `apps/marketing`,
  `packages/shared/src/connectAuth.ts`, `.github/workflows/release.yml`, and
  `docs/operations/release.md`.

The legacy Auldric repository at `cf6400e77dfaf9569f1ce6eaca4421deb0b2bf23` was donor evidence
only. Its `docs/auldric-branding.md`, `docs/auldric-migration-matrix.md`, distribution configuration,
and `docs/auldric-architecture.md` established usable Auldric desktop identifiers. Their global
hard-fork rules (`@auldric/*`, `AULDRIC_*`, `~/.auldric`, renamed provider context, and renamed wire
or telemetry identity) are rejected here because they conflict with T3 authority.

The current fork does not yet apply an Auldric distribution profile or contain the Marketing
implementation. The values below are the gate for that later bounded work, not evidence that an
Auldric installer or Marketing workspace already ships.

## Migration and release rules

1. **No branding migration.** Existing T3 installs, browser keys, mobile state, and `~/.t3` remain T3.
2. **Marketing is additive.** Its durable data migrations create Marketing-owned organization tables
   and never rename T3 events, projections, or storage.
3. **Separate distribution means separate install.** Auldric bundle, external scheme, updater,
   signing, and outer state values are configured together. A partial profile must fail release.
4. **No silent state import.** Auldric starts with isolated local runtime state. Canonical Marketing
   workspace data is recovered from its organization store after authorization, not copied from T3
   local state.
5. **Rollback follows ownership.** Marketing can be disabled without changing Dev; the Auldric
   public site and standalone package roll back independently; T3 state and release channels are
   never rollback targets for an Auldric change.

## Change review gate

Any change to a listed identifier family must answer all of these in review:

- Which matrix row owns it?
- Is it visible Marketing identity, T3 compatibility identity, or bounded distribution config?
- Does it change an existing user's wire, package, storage, callback, signing, or update identity?
- Can T3 and Auldric run concurrently without sharing a handler, lock, database, credential store,
  update feed, or release asset?
- Does disabling or rolling back Marketing restore native T3 behavior without data rewriting?

If ownership is unclear, keep the T3 value and amend this matrix before implementation.
