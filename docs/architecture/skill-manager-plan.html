Product exploration · July 2026

A skill manager for every harness, on every computer.

A settings page that inventories skill installations across connected T3 environments, explains which harnesses can use each one, copies remote paths, and eventually removes installations with guardrails.

Hightechnical viability
The read-only manager is a natural extension of T3 Code’s architecture. Every connected computer already runs a T3 environment server, and Codex/Claude provider snapshots already carry skill metadata and absolute paths. The real work is extracting this into a machine-level inventory service, adding adapters for the other harnesses, and treating filesystem mutation as a separately gated capability.

Recommended product shape

Default view: installation inventory

Group by computer, then show harness visibility beneath it. A concrete directory is the primary record. If one directory is visible to multiple harnesses, render it once with multiple harness badges—not as multiple independently deletable rows.

Scope: global first

V1 should inventory user/global skills. Project skills depend on a working directory and can only be complete for projects T3 knows about. Add a separate “Known projects” filter later, explicitly labeled as non-exhaustive.

What already exists, and what does not

Area Today Implication
Multi-computer model Connected environments already have stable IDs, labels, platform, connection state, and per-environment authenticated HTTP/WS sessions. No central cloud indexer is required. Query each online environment and merge client-side.
Codex skills The server calls Codex app-server skills/list and maps name, path, scope, and authoritative enablement when the harness exposes it. Reuse parsing knowledge, but inventory independently of a session cwd and configured provider status.
Claude skills T3 already scans the effective Claude config root and project .claude/skills, parsing SKILL.md frontmatter. Refactor the scanner behind a shared inventory adapter rather than duplicating it.
OpenCode skills No T3 inventory today. OpenCode supports native, Claude-compatible, agent-compatible, configured local, and even HTTP catalog sources. Filesystem roots are easy; config and remote catalogs need an OpenCode-specific adapter and read-only/remote source types.
Cursor skills Cursor is a provider in T3, but its provider snapshot does not expose skills. Scan documented user/project roots. Treat vendor-managed/built-in entries as non-removable unless ownership is proven.
Grok No supported local skill discovery contract was found in the current T3 driver. Return an explicit “not supported by this harness” state; do not guess directories.
Settings UI File-based settings routes and a sidebar make a new /settings/skills page straightforward. Add a dedicated page rather than embedding this in Providers.
Mutation API Provider skill paths are presentation data; there is no safe skill filesystem mutation endpoint. Build removal as a new capability with opaque IDs, root containment checks, and recoverable trashing.
Inventory caveat: “All skills” can only mean all discoverable skills on connected computers. Offline computers show cached results, and project-scoped discovery is bounded by known T3 projects—not every directory on disk.

Model installations, roots, and visibility separately

Skill root

A harness-declared source: absolute path or remote catalog, scope, ownership, mutability, and precedence. Examples: Codex user root, shared .agents root, plugin cache.

Installation

One concrete skill directory/file with canonical path, real path, metadata, validation state, modification time, and a stable scan-local ID.

Visibility

One or more harness instance IDs that consume the installation, plus effective/overridden/disabled status where the harness can report it.

Suggested contract

SkillInventory { scannedAt, roots[], installations[], diagnostics[] }. Each installation includes id, rootId, relativePath, display metadata, scope, source kind, consumers, capabilities, and health. Keep absolute paths for display, but never accept them back as mutation targets.

Identity and deduplication

Canonicalize with realpath and filesystem identity when possible. One symlinked installation can appear under several roots; retain aliases for explanation but choose one physical-installation record. Logical name equality alone is not deduplication.

Server and contracts

  • Add schema-only inventory contracts in packages/contracts and a new authenticated Environment HTTP API group.
  • Create SkillInventoryService in apps/server; adapters resolve roots from provider-instance settings and process environment, then scan best-effort with bounded concurrency.
  • Advertise skillInventory and later skillRemoval environment capabilities for version skew.
  • Cache the latest successful inventory per server home so offline/error UI has useful state; refresh manually and on relevant provider-settings changes.

Web client

  • Add /settings/skills, sidebar entry, environment-scoped query atoms, and an aggregate selector over the existing environment catalog.
  • Fetch only while the page is open; cap parallel environment requests and retain per-machine loading/error states.
  • Search across name, description, path, computer, and harness. Filters: online/offline, harness, scope, health, removable.
  • Use optimistic row removal only after the server reports the trash destination; then rescan that environment.
Why not reuse ServerProvider.skills directly? It is a runtime/provider snapshot, can depend on a cwd, omits unsupported harnesses and roots, may collapse name collisions, and lacks source ownership or safe mutation identity. It can seed adapters, but it is not an inventory contract.

Removal must be capability-based and recoverable

1 · Classify ownership

User-managed roots may be removed. Symlinked entries need a distinct unlink action. System, plugin-cache, HTTP catalog, and unknown sources are read-only.

2 · Re-resolve server-side

Client sends an opaque installation ID and inventory revision. Server resolves the registered root + relative path again, rejects traversal, root changes, unexpected type changes, and escaping symlinks.

3 · Trash, do not delete

Atomically move the whole skill installation to a T3-owned trash directory on that computer, write a manifest, and expose “Undo” while retained. Permanent deletion is unnecessary for V1.

Confirmation language

Show computer, physical path, all harnesses affected, aliases/symlinks, and whether another installation with the same skill name remains. Require a second confirmation when scripts or executable files are present.

Race and compatibility policy

Reject stale revisions with 409 and force a rescan. Old servers stay read-only because the capability is absent. Active sessions need no forced restart, but the UI should say the harness may not notice the change until its next session/refresh.

Never implement removal as “DELETE this absolute path.” Remote clients are untrusted input, and skill directories can contain symlinks, scripts, or vendor-managed content. The server must own root registration, containment, and mutation policy.

Phased implementation

Phase 0 · Spike

Lock the discovery matrix

Fixture real harness configs; validate Codex/Claude custom homes, shared roots, symlinks, collisions, OpenCode config sources, and Cursor roots. Decide V1’s exact supported scopes.

Phase 1 · Read-only MVP

Inventory global skills

Contracts, capabilities, server adapters for Codex + Claude, per-environment endpoint, settings page, grouping, search, copy path, refresh, errors, and stale/offline presentation.

Phase 2 · Coverage

Add OpenCode + Cursor

Compatibility-root dedupe, configured OpenCode local sources, harness visibility badges, validation diagnostics, and known-project scope behind a filter.

Phase 3 · Management

Recoverable removal

Trash/undo service, ownership policy, stale-scan protection, confirmation UX, mutation audit log, and capability-gated UI.

Keep install/edit/sync out of the first project. Those require conflict resolution, copying supporting files across computers, provenance, and potentially a canonical skill registry—valuable, but a distinct product.

Verification strategy

Backend focused tests

  • Per-adapter fixture trees and custom-home resolution
  • Malformed frontmatter and unreadable roots remain diagnostics, not request failures
  • Precedence, duplicate names, canonical-path dedupe, and symlink aliases
  • Containment, stale revision, read-only roots, trash manifest, and undo
  • Windows path semantics and cross-device move fallback

Frontend and integrated tests

  • Aggregate online, offline, unsupported, old-server, empty, and partial-failure environments
  • Grouping/search/filter behavior and copy-path fidelity
  • Removal confirmation lists every affected harness
  • Run focused component/logic tests, targeted formatting/lint/type checks
  • Complete one isolated test-t3-app browser verification of the settings flow after implementation

Decisions to make before implementation

  1. Does V1 mean global/user skills only? Recommended: yes. Add known-project discovery after the global model is sound.
  2. Should shared physical installations appear under every harness or once? Recommended: once per machine, with consumer badges and optional “group by harness” presentation.
  3. Is removal permanent? Recommended: no. “Move to trash” with undo is the only initial mutation.
  4. Do we support only configured provider instances? Recommended: scan roots for configured harness instances, plus recognized shared roots; do not probe arbitrary software installations.
  5. How long should offline inventory persist? Recommended: cache the last successful scan until the environment is unlinked, with a prominent timestamp.
Suggested go/no-go: proceed with a narrow read-only MVP for Codex and Claude. It delivers most of the immediate value, proves the cross-computer aggregation model, and creates the safe foundation needed for broader harness coverage and removal.
