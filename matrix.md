## Findings first

1. **Proof remains incomplete.** The current PR description contains no captures. Still images cannot establish a paused timer, resumed elapsed time, or fold interaction. Record the sequences below and include main/head comparisons for the changed behavior. Existing unit tests are useful numeric oracles but do not establish rendered behavior.
2. **No first-party OAuth is required for the core captures.** A source dev server registers **Replay (dev)**. Its displayed scenarios **Question** and **Write approval** block until the UI answers and exercise the real ACP adapter, orchestration, persisted turn items, and clients. Identify these captures as “real app, replay provider”; they do not prove a paid provider's behavior.
3. **The replay Question scenario alone cannot prove Worked-for totals.** It contains a question and final answer, with no ordinary foldable work. An answered question stays visible, so a fold need not exist. Use Write approval for real-app totals, and a labelled harness with a command before/after a question for exact question totals. The built-in replay resumes and completes quickly; it is sufficient for waiting and completion but may not leave enough time to read the resumed timer. Use a scratch-only ACP driver with an explicit post-answer work gate, or label a component harness, for that proof.
4. **Do not omit the alternate calculations.** Latest-run duration uses run start/end; older/runless duration uses prompt/item boundaries; per-steer duration clips the same waits to the segment. Live app runs may inherit a predecessor's start, whereas runless work only owns runless requests after its response boundary. These look similar but need independent fixture data.
5. **Scope limits should remain explicit.** The sidebar timer is unchanged; it can disagree after an answer. An answered wait outside loaded history cannot be deducted. Guest does not pass the runless-active flag. Secret/environment-link requests are outside `isUserWaitItem`. Native-subagent requests can pause the owning run's entire timer. No new merge-blocking code defect is asserted by this proof-planning pass.

## Seeding recipes

**R-Q / R-A: real app, replay provider.** Start an isolated fresh source server with `T3CODE_DEV_SEED=0 vp run dev`, without explicit origin variables and without the live T3 home. Read actual ports from its output. Add/open a scratch project and create a thread. Select **Replay (dev)**, then the displayed **Question** or **Write approval** scenario, send any short prompt, and open `/<environmentId>/<threadId>`. The scenario controls playback, not prompt wording. Use **Supervised** (`approval-required`) for approval capture; the replay emits the recorded request deterministically. A question does not require a narrower runtime; Full access still blocks on its recorded question. Leave it unanswered at least 10 seconds on camera, answer in the UI, then capture completion. For minute-exclusion proof, use a longer explicit dwell or the deterministic timeline below. Do not assert the replay actually wrote a file: it replays tool events and intentionally drops terminal execution.

**R-H: real app, custom replay driver.** For a legible post-answer timer and exact lifecycle ordering, the capturer may create a scratch-only local ACP command outside the worktree, register it under Settings → Providers, and emit the same permission/elicitation frames as the built-in replay, plus ordinary tool activity and a separate post-answer gate. Use the existing dev replay implementation as the protocol reference. Await UI answers/gates, not accidental provider pacing. This is a proposed driver recipe, not a driver delivered or verified by this audit. Until implemented, rows requiring it can use H and must retain the harness label.

**H: labelled harness.** There is no discovered public RPC that manufactures arbitrary turn-item timestamps, run ownership, imported history, or overlapping pending requests. Do not mutate the live database. Supply typed projected items to the real web timeline derivation/rendering or mobile feed/timer consumers in an isolated capture harness; label it **“Harness: synthetic turn items”**. Include the run summaries and timestamp data in its manifest. This is the deterministic fallback for the rows marked H. Existing test fixture providers are test-layer tools, not a shipped UI fixture route.

**Paid-provider alternative.** If already configured in the isolated server, Codex in Supervised with a local write needing approval is an approval path; OpenCode has recorded question/permission support, and Grok has recorded ACP approval support. Ask OpenCode to use its question tool. Treat actual emission as unverified until observed; a prompt requesting a question is not proof of `user_input_request`. Pi/Cursor availability alone does not establish a blocking request. Do not spend capture time repairing OAuth or routing. Prefer replay for determinism. Codex message-mode questions are deliberately nonblocking and belong to F9, not F1.

**D: desktop.** Connect Electron to the isolated source environment if supported by the chosen dev setup, or explicitly configure the same local ACP replay command in its isolated server. Bundled desktop servers do not auto-register Replay (dev). No shell/IPC changes are in this diff; one integrated lifecycle is enough for desktop coverage.

**G: guest.** A real guest capture requires a guest share from the thread's Share with guest flow and its returned `/guest` URL, backed by the configured sharing/relay path. Never publish its invite credential. If that infrastructure is absent, capture the GuestPage timeline inputs in H and label it; do not claim real guest verification. Answer requests in the owner client, since guest is an observing/proposing surface.

**M: mobile.** Connect the native app to the same isolated server, open the seeded thread, and drive the answer from the native UI. Use the shared Android/iOS pool and normal mobile verification/install workflow. Capture each native platform at its actual device dimensions, recording the dimensions and theme. No browser emulation is evidence of React Native rendering.

## Numeric edge manifest (collapse into F11/F12, existing tests can prove arithmetic)

| Input equivalence class | Oracle / visible consequence |
| --- | --- |
| No waits / nonblocking message-mode question | Original elapsed work is retained. |
| Null request start / reversed or empty interval | No deducted span; an own open blocking item can still select waiting even if it has no usable start. |
| Overlap/nesting/disjoint and out-of-order requests | Sorted union, count every millisecond once; F11 uses a visible two-request exit. |
| Wait begins before run / finishes after measured end / open at completed end | Clip to duration window; open request contributes to end for settled calculation. |
| Live request begins before timer start / remains open | Live start adjustment ignores it; own-open determination still decides waiting separately. |
| All measured time is waiting / reversed run duration | Clamp worked result to zero; current formatter displays `1ms` for zero. |
| Runless foreign request / app-run predecessor wait | Runless filters other run IDs; app-run inherited timer can include answered waits from other runs since its start. |
| Non-finite ISO parsing in H | Settled fallback label without duration. Valid schema data should not require this screenshot to establish ordinary app behavior. |
