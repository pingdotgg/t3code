Measured latency, not an inferred bottleneck

A live Kilo resume spent about 4.9 seconds in initialize, 4.8 seconds creating a session that was immediately discarded, 0.9 seconds loading the persisted session, and 6.6 seconds before first prompt output. Removing the redundant new session saves roughly five seconds on process reactivation. ACP does not define a cheap portable health endpoint, so complete auth/model discovery remains asynchronous and bounded.

What to borrow from active VS Code theme search

  • One explicit query with useful suggested searches.
  • Deterministic loading, error, empty, and results states.
  • Compact rows with name, author, description, license, source, and a local action.
  • Cancel stale searches and keep the busy state on the selected row.
  • Derive “Already added” from local state instead of trusting the remote catalog.

What must differ from theme search

  • Search and provision through WebSocket RPC, never from the browser.
  • Resolve only distributions compatible with the target environment.
  • Do not invent popularity. The ACP index has no trustworthy download metric.
  • Use only allowlisted official registry icons, cache them in the browser, and retain a neutral ACP fallback for load failures.
  • The Add click is explicit consent to provision third-party code.

PRs #1601, #2684, and the open #6071 all grew a second runtime or broader lifecycle. Review feedback on #6071 also caught silent remote execution, lying readiness, argument round-trip corruption, placeholder model selection, and process stop races. This plan reuses the v2 adapter and avoids each of those surfaces.

Interaction

  1. User selects ACP Registry in the existing Add Provider dialog.
  2. The step immediately loads all compatible official entries for the selected environment; entering a query narrows them.
  3. User clicks Add on one result. That click authorizes provisioning.
  4. The server prepares the distribution. The row shows static state text such as “Downloading” or “Preparing,” without a continuously repainting animation.
  5. On success, the display name is prefilled with the agent name and the instance ID follows the wizard’s existing deriveInstanceId convention (for example acpRegistry_gemini-cli), with a suffix when the derived ID already exists. The provider settings are then persisted.
  6. The completion message links to the agent’s source/docs and explains that authentication, when required, remains user-owned.

Step-order note: today the wizard runs Driver → Identity → Config, and resolveWizardNavigation gates forward movement past Identity on a valid instance ID. The ACP flow above runs search before identity, so the step model becomes driver-aware for acpRegistry: Driver → Find ACP → Identity, with the search result feeding the identity prefill.

Technical design

Turn the existing resolver into a single server-scoped ACP Registry catalog service. The service is shared by WebSocket handlers, provider snapshots, and the v2 adapter, so catalog validation and distribution selection cannot drift.

Web / desktop Search + Add UI Environment-scoped client state. Derives “Added” from current provider settings.
→
Contracts 3 typed RPCs Search, prepare, and managed-binary uninstall. Health discovery uses the normal provider snapshot flow.
→
Server singleton ACP Registry catalog Fetch, validate, rank, resolve, inspect cache, and prepare one compatible entry.
→
Existing runtime v2 ACP adapter Starts the pinned recipe during a normal turn and owns all ACP session behavior.

RPC 1: search

server.searchAcpRegistry({ query }) → { agents: [{ id, name, version, description, authors, license, website, repository, distribution, integrity }] }
  • Read scope.
  • Empty query can return the compact compatible catalog.
  • Rank exact ID/name, prefix, token, then description/author match.
  • Stable result cap and bounded metadata fields.
  • No persisted state and no executable download.

RPC 2: prepare

server.prepareAcpRegistryAgent({ agentId }) → { agentId, version, distribution, prepared: true }
  • Operate scope.
  • Re-fetches and re-validates the selected ID instead of trusting UI metadata.
  • Idempotent across retries and concurrent clients.
  • Returns only after the distribution is usable by the existing resolver contract.
  • Does not write settings. The existing settings RPC runs only after prepare succeeds.

Distribution semantics

DistributionPrepare behaviorRuntime behaviorUI language
binary Download into the existing versioned cache, verify declared SHA-256, validate archive paths, then atomically rename. Spawn the prepared executable from the target environment cache. “Downloading” then “Added”
npx Validate the exact version-pinned recipe and that npx exists. Do not start the ACP agent during setup. npx --yes materializes the pinned package on first normal session. “Preparing” then “Added”
uvx Validate the exact version-pinned recipe and that uvx exists. Do not start the ACP agent during setup. uvx materializes the pinned package on first normal session. “Preparing” then “Added”

This is the narrowest honest definition of automatic provisioning: the user never copies an install command, but T3 also does not launch arbitrary third-party ACP processes during a settings operation. Binary downloads are eager because the current resolver already owns a safe managed cache. Runner-based packages stay runner-managed.

Registry hardening

  • Bound fetch time and response bytes.
  • Decode optional authors, license, source URLs, and SHA-256.
  • Require HTTPS download/source URLs with no embedded credentials.
  • Verify SHA-256 when present. Keep supporting official rows that omit it; 8 of 38 agents do today.
  • Preserve current archive size, traversal, executable-root, and lock checks.

Search freshness

  • Already built: single-flight fetch, atomic JSON persist, and offline fallback to the last validated disk copy.
  • New: the in-memory index currently memoizes forever after first load; explicit searches must refresh it.
  • Resolver uses the most recent validated in-memory index.

Status correction

  • No agent ID: not installed, unconfigured message.
  • Unsupported platform or missing runner: error, not ready.
  • Prepared/runner available: installed, ready, registry version.
  • Fast refresh re-inspects catalog/cache/runner and publishes readiness without waiting for an ACP process.
  • A bounded background enrichment starts a disposable session to discover generic auth state, models, and slash commands.
  • Auth-required probes fail fast and never call ACP authenticate, OAuth, or a terminal flow.

Authentication boundary

T3 does not collect, copy, migrate, or store ACP credentials. Automatic discovery starts a bounded disposable session but explicitly disables authenticate-and-retry. If the agent reports auth required, T3 records its advertised generic method and tells the user to complete it on the server. A real conversation may use the ACP protocol's normal agent-managed authentication flow. Terminal-only login remains a manual server step.

Round 3: ACP standardization and subagent repair, proven

Resolved: current Codex elicitation crossed a legacy ACP boundary

codex-acp 1.2.0 sends elicitation/create and expects the current flat response {"action":"accept"}. T3's pinned ACP 0.11.3 schema registered only session/elicitation and encoded a nested action. Codex translated that protocol mismatch into a cancelled MCP call before child creation.

The compatibility boundary now registers both method generations. Internally both use a flat normalized action; only the legacy wire response is converted back to the nested shape. Exact JSON-RPC request IDs travel beside decoded requests, so approval routing no longer depends on raw payload queues or schema-shape correlation.

Standardized in this PR

  • First-class transport request context for all typed core and extension request handlers.
  • One approval translation for standard permission requests and tagged MCP approval elicitations.
  • One provider-neutral T3 instruction bundle, re-applied only when the interaction mode changes.
  • One ACP session configuration projection for select, boolean, and model options.
  • One MCP delivery boundary: stdio for compliant agents and the same authenticated, thread-scoped tools through acp-mcp-call when an agent drops injected servers.
  • One current/legacy elicitation normalizer instead of upgrading the entire pinned schema and breaking older agents.
  • One response-admission lifecycle keyed by the real transport ID across restart, Stop, and stale generations.
  • One live command and skill refresh path, including cached provider snapshots.

Deleted complexity

  • No second queue of raw requests inside the orchestration adapter.
  • No canonical JSON comparison or decoded-subset heuristic.
  • No request correlation based on session IDs, tool-call IDs, messages, schemas, or provider extensions.
  • No Codex-only execution path for ordinary ACP request identity.
  • No silent fallback from a missing transport identity to an unrelated pending request.
